# Ассистент внедренца

AI-помощник руководителя проектов внедрения. Закрывает цикл «встреча, задачи,
следующая встреча».

## Задача

Внедренец ведет несколько проектов одновременно. После каждой встречи остаются
заметки, из которых нужно вытащить договоренности, завести задачи, поставить
сроки и не потерять то, что обещал заказчик. На практике это делается вручную
или не делается вовсе, а перед следующей встречей человек вспоминает по памяти,
о чем договаривались в прошлый раз.

**После встречи.** Сотрудник присылает заметки текстом или файлом. Ассистент
разбирает их, выделяет задачи с ответственными и сроками, отличает работу на
своей стороне от работы на стороне заказчика, узнает то, что уже есть в
реестре, переводит «до конца недели» в конкретную дату. Показывает результат на
подтверждение и только после согласия записывает новые задачи и меняет сроки
существующих.

**Перед встречей.** Ассистент поднимает историю проекта. Этап, сроки с остатком
рабочих дней, процент выполнения, что закрыто с прошлой встречи,
договоренности, открытые и просроченные задачи, вопросы на встречу и риски.

Реестр задач здесь единственный источник правды. Договоренность о встрече
попадает туда же обычной задачей, ведь встречу все равно нужно готовить.

## Как это работает

```
веб-чат / Telegram  →  агент (LLM + function calling)  →  реестр проектов
                                  ↓
                           журнал действий
```

| Инструмент | Действие |
|---|---|
| `get_project_context` | карточка проекта, встречи, открытые и просроченные задачи |
| `list_overdue_tasks` | просроченное, ближайшее, отдельно задачи без срока |
| `find_similar_tasks` | повторяющиеся задачи у разных заказчиков |
| `add_tasks` | **запись** новых задач в реестр |
| `update_task` | **изменение** срока или статуса задачи |

Документы в форматах PDF, DOCX, TXT, MD и CSV разбираются наравне с
напечатанным текстом. Из DOCX извлекаются в том числе таблицы, ведь в
техзаданиях требования чаще лежат именно там. Получив ТЗ, ассистент не
пересказывает его, а сверяет требования с реестром и говорит, чего в документе
не хватает.

## Что сделано сверх минимального прототипа

Прототип с LLM легко довести до состояния «отвечает красиво, но доверять
нельзя». Ниже то, что отделяет одно от другого.

**Подтверждение перед записью.** Ассистент показывает, что собирается записать,
и ждет согласия.

**Защита от выдуманных номеров.** Ответ сканируется на упоминания вида `T-004`
и сверяется с реестром. Если номера не существует, ответ возвращается модели с
требованием исправить. Ссылка на несуществующую задачу звучит уверенно и
проверяется трудно, это самая опасная ошибка в таком инструменте.

**Защита от дублей.** Перед записью задача сравнивается с открытыми задачами
проекта. Дубль не создается, а возвращается человеку с номером существующей
задачи.

**Асимметрия при закрытии задач.** Закрыть задачу можно только при явном
указании, что работа сделана. При сомнениях ассистент переносит срок, ведь
незакрытая задача попадется на глаза, а закрытая по ошибке исчезнет бесследно.

**Все, что можно посчитать, считает код.** Даты, просрочки в днях, остаток
рабочих дней, проценты, форматирование. Модель получает готовые значения.
Промпт отвечает за формулировки, код за факты.

**Правила живут рядом с инструментами.** Условия вызова, запреты и формат
аргументов описаны в самих инструментах, а не собраны в общем промпте. При
добавлении нового инструмента правила приезжают вместе с ним.

**Ошибки инструментов направляют модель.** Вместо «неверный формат» инструмент
отвечает, что именно исправить и что сделать дальше. Модель чинится сама на
следующем шаге.

## Стек

Python, FastAPI, OpenAI SDK в совместимом режиме, Google Sheets API.

Реестр живет в Google Таблице. Данные видны и правятся руками, а структура
повторяет то, как внедренцы ведут проекты в реальности. В продуктиве на это
место встает Битрикс24 или 1С, и меняется только модуль `sheets.py`.

Ядро агента не знает, откуда пришло сообщение. Веб-версия показывает журнал
вызовов инструментов рядом с диалогом. Telegram удобнее, когда нужно
надиктовать заметки сразу после встречи. Консольный режим `cli.py` служит для
отладки.

## Запуск

Нужен Python 3.9 или новее.

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Скопируйте `.env.example` в `.env` и впишите один ключ.

```
LLM_API_KEY=<ключ из Google AI Studio>
```

Ключ выдается бесплатно за пару минут, карта не нужна. Больше ничего
настраивать не требуется. Пока в папке нет файла `credentials.json` и не
заполнена переменная `SHEET_ID`, проект работает в демо-режиме и пишет реестр в
локальный файл `demo_workspace.xlsx`. Работают все сценарии, включая запись
задач, а результат видно прямо в файле.

Проверка доступов, делайте ее первой.

```bash
python check_setup.py
```

Запуск.

```bash
uvicorn web:app --reload    # веб-интерфейс на http://127.0.0.1:8000
python bot.py               # Telegram-бот
python cli.py               # консоль, для отладки
```

### Другой провайдер модели

Проект обращается к модели через OpenAI-совместимый интерфейс, поэтому подойдет
любой провайдер с таким же API. Меняются две строки в `.env`.

| Провайдер | LLM_BASE_URL | Пример модели |
|---|---|---|
| Google Gemini | `https://generativelanguage.googleapis.com/v1beta/openai/` | `gemini-3.6-flash` |
| OpenAI | `https://api.openai.com/v1` | `gpt-5-mini` |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-v4-flash` |
| OpenRouter | `https://openrouter.ai/api/v1` | `openai/gpt-5-mini` |
| GigaChat | `https://gigachat.devices.sberbank.ru/api/v1` | `GigaChat-2` |
| Ollama | `http://localhost:11434/v1` | `qwen3:8b` |

Для локального сервера `LLM_API_KEY` можно не заполнять. Главное требование к
модели это поддержка вызова инструментов, без нее агент не работает.

### Полный режим с Google Таблицей

Нужен, если хочется увидеть запись в настоящий сервис.

1. В Google Cloud Console включите Sheets API, создайте сервисный аккаунт и
   скачайте JSON-ключ в файл `credentials.json`.
2. Загрузите `potok_demo_data.xlsx` на Диск, откройте как Google Таблицу и
   выдайте сервисному аккаунту права редактора. Идентификатор из адресной
   строки положите в `SHEET_ID`.

### Telegram-бот

Добавьте в `.env` токен от @BotFather и свой числовой идентификатор от
@userinfobot.

```
TELEGRAM_TOKEN=
ALLOWED_USER_ID=
```

Без `ALLOWED_USER_ID` бот отвечает всем, кто найдет его по имени. Умеет то же,
что и веб. Кнопки открывают список проектов, сводку по просроченному и
подготовку к встрече, документы отправляются вложением.

## Проверка качества

Промпт правится вслепую, если проверять его глазами на одном примере. Каждая
вторая правка ломает то, что работало раньше.

```bash
python evals.py
```

Скрипт прогоняет десять сценариев и проверяет результат программно. Смотрит не
только текст ответа, но и то, какие инструменты вызваны и с какими аргументами.
Работает в демо-режиме, потому что перед каждым сценарием возвращает реестр в
исходное состояние.

```bash
python evals.py --repeat 3    # ответы модели неустойчивы
python evals.py --verbose     # печатать ответы целиком
```

Последний результат, `gemini-3.5-flash-lite`, десять сценариев из десяти, ноль
ошибок в инструментах. Так же сравниваются модели между собой.

Ручной чек-лист для проверки интерфейса лежит в `TESTS.md`.

## Демонстрационные данные

Файл `potok_demo_data.xlsx` содержит три вымышленных проекта внедрения с
историей за три месяца. Часть задач намеренно просрочена, у части ответственный
на стороне заказчика, несколько задач повторяются у разных клиентов.

Что попробовать.

- `Подготовь меня к встрече с ТехноСнабом`, бриф с историей, задачами и рисками
- `Что горит на этой неделе?`, сводка по всем проектам
- Вставить заметки со встречи, подтвердить, увидеть задачи в реестре
- Прислать ТЗ файлом и получить требования, сверенные с реестром

## Ограничения

- **Процент выполнения это грубая метрика.** Задачи разного веса считаются
  одинаково.
- **Рабочие дни считаются без праздников.**
- **Даты закрытия задач в реестре нет.** Строка «закрыто с прошлой встречи»
  считается по сроку задачи. Этого хватает, чтобы показать движение, но не
  хватает для настоящей истории проекта.
- **Проверяются идентификаторы, а не содержание.** Если модель припишет встрече
  договоренность, которой не было, код этого не увидит.
- **История диалога хранится в памяти процесса.** Прототип рассчитан на одного
  пользователя.
- **Поиск по проектам работает перебором.** При сотнях проектов понадобится
  индекс или векторный поиск.
- **Аутентификации в веб-версии нет.** В Telegram доступ ограничен одним
  идентификатором.

## Что дальше

1. **Интеграция с CRM и 1С.** Главное направление. Задачи ставятся прямо в
   Битрикс24, оттуда же берутся сделки, ответственные и сроки. Слой доступа к
   данным изолирован в одном модуле, поэтому замена не затрагивает логику
   агента. Туда же ложатся календарь и уведомления, ведь в Битрикс24 они уже
   есть.
2. **Голосовой ввод.** Надиктовать заметки с телефона по дороге со встречи.
3. **Журнал изменений.** Каждое изменение задачи с датой, автором и причиной.
   Даст динамику проекта и аудит действий ассистента.
4. **Проактивный дайджест.** Утренняя сводка по зависшим задачам без запроса.
5. **Векторный поиск по документам.** Понадобится, когда материалов станет
   больше, чем помещается в контекст.
