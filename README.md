# Ассистент внедренца

AI-помощник руководителя проектов внедрения. Закрывает цикл
**встреча → задачи → следующая встреча**.

## Задача

Внедренец ведёт несколько проектов одновременно. После каждой встречи
остаются заметки, из которых нужно вытащить договорённости, завести задачи,
поставить дедлайны и не потерять то, что обещал заказчик. На практике это
делается вручную или не делается вовсе, а перед следующей встречей человек
вспоминает по памяти, о чём договаривались в прошлый раз.

Ассистент закрывает обе стороны цикла.

**После встречи.** Сотрудник присылает заметки текстом, голосом или файлом.
Ассистент разбирает их: выделяет задачи с ответственными и сроками, отличает
работу на своей стороне от работы на стороне заказчика, распознаёт, что уже
есть в реестре, переводит «до конца недели» в конкретную дату. Показывает
результат на подтверждение и только после согласия записывает задачи в
реестр, меняет сроки существующих и ставит события в календарь.

**Перед встречей.** Ассистент поднимает историю проекта: этап, сроки с
остатком рабочих дней, процент выполнения, что закрыто с прошлой встречи,
договорённости, открытые и просроченные задачи, вопросы на встречу и риски.

Реестр наполняется первой половиной цикла и используется второй. Чем дольше
работает система, тем больше в ней контекста.

## Как это работает

```
веб-чат / Telegram  →  агент (LLM + function calling)  →  Google Sheets / Calendar
                                  ↓
                           журнал действий
```

Агент получает сообщение, сам решает, какие инструменты вызвать, и выполняет
их последовательно, пока не соберёт ответ.

| Инструмент | Действие |
|---|---|
| `get_project_context` | карточка проекта, встречи, открытые и просроченные задачи |
| `list_overdue_tasks` | просроченное, ближайшее, отдельно — задачи без срока |
| `find_similar_tasks` | повторяющиеся задачи у разных заказчиков |
| `add_tasks` | **запись** новых задач в реестр |
| `update_task` | **изменение** срока или статуса задачи |
| `create_deadline` | **создание** события в Google Calendar |

Документы — PDF, DOCX, TXT, MD, CSV — разбираются наравне с напечатанным
текстом. Из DOCX извлекаются в том числе таблицы: в техзаданиях требования
чаще лежат именно там. Получив ТЗ, ассистент не пересказывает его, а сверяет
требования с реестром задач и говорит, чего в документе не хватает.

## Что сделано сверх минимального прототипа

Прототип с LLM легко довести до состояния «отвечает красиво, но доверять
нельзя». Ниже то, что отделяет одно от другого.

**Подтверждение перед записью.** Ассистент показывает, что собирается
записать, и ждёт согласия. Автоматическая запись без спроса в рабочем
инструменте недопустима.

**Защита от выдуманных номеров.** Ответ сканируется на упоминания `T-004`,
`M-005`, `P-002` и сверяется с реестром. Если номера не существует, ответ не
показывается человеку, а возвращается модели с требованием исправить.
Ссылка на несуществующую задачу звучит уверенно и проверяется трудно — это
самая опасная ошибка в таком инструменте.

**Защита от дублей.** Перед записью задача сравнивается с открытыми задачами
проекта по доле общих слов. Дубль не создаётся, а возвращается человеку с
номером уже существующей задачи.

**Асимметрия при закрытии задач.** Закрыть задачу можно только при явном
указании, что работа сделана. При сомнениях ассистент переносит срок, а не
закрывает: незакрытая задача попадётся на глаза, закрытая по ошибке
исчезнет бесследно.

**Всё, что можно посчитать, считает код.** Даты, просрочки в днях, остаток
рабочих дней, проценты, форматирование — детерминированная логика. Модель
получает готовые значения и не пересчитывает их. Промпт отвечает за
формулировки, код — за факты.

**Правило и в промпте, и в коде.** Критичные инварианты продублированы:
промпт может подвести на слабой модели, код не может.

## Стек

Python, FastAPI, OpenAI SDK в совместимом режиме, Google Sheets API, Google
Calendar API. Модель — Gemini 3.x Flash.

Провайдер модели — параметр конфигурации: Gemini и GigaChat совместимы по
формату вызовов, переключение делается двумя строками в `.env` без правки
кода. Для российского контура это не абстракция, а рабочий сценарий.

Реестр живёт в Google Таблице: данные видны и правятся руками, а структура
повторяет то, как внедренцы ведут проекты в реальности. В продуктиве на это
место встаёт Битрикс24 или 1С — меняется только модуль `sheets.py`.

Ядро агента не знает, откуда пришло сообщение. Веб-версия показывает журнал
вызовов инструментов рядом с диалогом, Telegram удобнее для реального
сценария: надиктовать заметки сразу после встречи, не открывая ноутбук.
Консольный режим (`cli.py`) — инструмент отладки, не интерфейс для
пользователя.

## Запуск

Нужен Python 3.9+. Проверено на macOS с 3.9 и Windows с 3.13.

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Скопируйте `.env.example` в `.env` и заполните:

1. **Ключ модели** — Google AI Studio, бесплатный тариф, карта не нужна.
2. **Сервисный аккаунт Google** — в Cloud Console включите Sheets API и
   Calendar API, создайте сервисный аккаунт, скачайте JSON в
   `credentials.json`.
3. **Таблица** — загрузите `potok_demo_data.xlsx` на Диск, откройте как
   Google Таблицу, выдайте сервисному аккаунту права редактора. ID — из
   адресной строки. Лист `projects` содержит колонку `planned_finish` —
   плановую дату завершения, по ней считается остаток рабочих дней.
4. **Календарь** — создайте отдельный календарь, выдайте сервисному аккаунту
   право изменения событий. ID — в настройках календаря.

Проверка доступов перед запуском:

```bash
python check_setup.py
```

Запуск:

```bash
uvicorn web:app --reload    # веб-интерфейс на http://127.0.0.1:8000
python bot.py               # Telegram-бот, нужны TELEGRAM_TOKEN и ALLOWED_USER_ID
python cli.py               # консоль, для отладки
```

## Демонстрационные данные

`potok_demo_data.xlsx` — три листа: проекты, встречи, задачи. Три вымышленных
проекта внедрения с историей за три месяца. Часть задач намеренно
просрочена, у части ответственный на стороне заказчика, несколько задач
намеренно повторяются у разных клиентов.

Что попробовать:

- `Подготовь меня к встрече с ТехноСнабом` — бриф с историей, задачами и рисками
- `Что горит на этой неделе?` — сводка по всем проектам
- Вставить заметки со встречи → подтвердить → задачи в реестре и календаре
- Прислать ТЗ файлом → требования, сверенные с реестром
- `/similar` в боте — повторяющиеся задачи у разных заказчиков

## Ограничения

Названы честно, потому что понимать границы решения важнее, чем скрывать их.

- **Процент выполнения — грубая метрика.** Задачи разного веса считаются
  одинаково. Честный вариант требует трудозатрат в каждой строке реестра, для
  прототипа это избыточно.
- **Рабочие дни считаются без праздников.** Производственный календарь нужно
  вести отдельно и обновлять ежегодно.
- **Даты закрытия задач в реестре нет.** «Закрыто с прошлой встречи»
  считается по сроку задачи — этого хватает, чтобы показать движение, но
  не хватает для настоящей истории проекта. Полноценная динамика требует
  журнала изменений, он в планах ниже.
- **Проверяются идентификаторы, а не содержание.** Если модель припишет
  встрече договорённость, которой не было, код этого не увидит. Полная
  сверка утверждений с источником дорога и в прототип не входит.
- **История диалога хранится в памяти процесса**, рассчитана на одного
  пользователя, перезапуск её очищает.
- **Бесплатный тариф модели ограничен** несколькими запросами в минуту. При
  упоре в лимит агент ждёт и повторяет автоматически.
- **Поиск по проектам работает перебором.** При сотнях проектов понадобится
  индекс или векторный поиск.
- **Аутентификации нет** в вебе; в Telegram доступ ограничен одним
  Telegram ID.

## Что дальше

1. **Битрикс24 или 1С вместо таблицы** как источник задач и сделок —
   основной сценарий для реального заказчика.
2. **Голосовой ввод** — надиктовать заметки с телефона по дороге со встречи
   вместо того, чтобы печатать.
3. **Журнал изменений** — каждое изменение задачи с датой, автором и
   причиной. Даст и настоящую динамику проекта (сколько раз двигали сроки
   и почему), и аудит действий ассистента, без которого в корпоративном
   внедрении не обойтись.
4. **Проактивный дайджест** — утренняя сводка по зависшим задачам без
   запроса.
5. **Векторный поиск по документам проекта** — когда материалов станет
   больше, чем помещается в контекст. Сейчас это было бы преждевременным
   усложнением.
